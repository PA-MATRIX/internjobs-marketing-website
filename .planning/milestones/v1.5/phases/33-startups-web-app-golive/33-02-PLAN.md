<objective>
Extend the zone-wide Cloudflare Email Routing catch-all Worker (`internjobs-email-ingest`, `apps/email-worker`) so that mail addressed to `@employers.internjobs.ai` is dispatched to the startup pipeline, without touching its existing `agent.internjobs.ai` conversation-alias behavior or its operator-fallback safety net.

**Why this Worker changes (not a new CF Email Routing rule):** Cloudflare Email Routing has exactly **one zone-wide catch-all** for `internjobs.ai`, already bound to this Worker (verified via CF API: `matchers:[{type:"all"}]`). The dashboard's per-subdomain view is cosmetic — there is no way to add an independent `employers.internjobs.ai`-only catch-all without repointing (and breaking) the existing rule. So this Worker — which already owns "classify the recipient and decide what to do" — is the correct place to add the new branch. It is a plain-JS, schema-agnostic dispatcher by design (no knowledge of `startup_channel_links` or Postgres); rather than duplicate the startup app's slug-resolution + MIME-parsing + insert logic here, this Worker hands the raw mail off over HTTPS to a new endpoint on the startup Worker (`apps/startup`, Plan 33-01, executed in parallel against the same documented contract below).

**Contract with Plan 33-01 (apps/startup) — both plans were written against this exact contract, do not deviate:**
- URL: `https://mcp.internjobs.ai/internal/email/inbound` (new `vars.STARTUP_EMAIL_HANDOFF_URL` binding in this Worker's `wrangler.toml`)
- Method: `POST`
- Headers this Worker sends: `Authorization: Bearer <EMAIL_HANDOFF_SECRET>` (new shared secret, provisioned in Plan 33-04 — same value bound to BOTH this Worker and `apps/startup`), `Content-Type: message/rfc822`, `X-Startup-To: <recipient address>`, `X-Startup-From: <message.from>`
- Body: exact raw MIME bytes (`ArrayBuffer`, NOT JSON — preserves postal-mime-compatible bytes on the receiving end without a lossy text round-trip)
- Response: `200` = success, do nothing further. ANY non-2xx / thrown error / timeout = treat as failure and fall through to the existing `message.forward(OPERATOR_FALLBACK)` safety net (same fallback already used for every other failure mode in this file) — this is the fail-safe behavior the phase requires for unresolvable/unknown employers slugs (the startup Worker returns `404` for those, which this Worker treats the same as any other non-2xx: forward, don't drop).
- **End-to-end latency budget (fixes a checker-flagged blocker — this Worker owns the OUTER ceiling AND the overhead budget, Plan 33-01 owns the inner fetch sum; iteration 2 revision: genuine headroom + mechanical CI enforcement, not a token margin and comment-only discipline):** `dispatchToEmployersHandoff()`'s single outer timeout wraps the ENTIRE outer POST — which is more than just the two inner fetches it's compared against. On the receiving end, Plan 33-01's `processInboundEmail()` runs `RESOLVE_TIMEOUT_MS` (4000ms) + `INSERT_TIMEOUT_MS` (5000ms) = 9000ms of sequential fetches, but the outer POST this Worker times ALSO pays for: TLS/connection setup + transmission of the raw MIME body (potentially large with attachments), `postal-mime` parsing CPU that runs BETWEEN the two inner fetches (budgeted in neither inner timeout), and response transmission back. This Worker therefore defines a separate `OVERHEAD_BUDGET_MS = 5000ms` to cover that non-fetch time, and raises its outer `EMPLOYERS_HANDOFF_TIMEOUT_MS` to **`20000ms`** (up from a too-tight `10000ms` in the prior revision), so the full invariant `RESOLVE_TIMEOUT_MS + INSERT_TIMEOUT_MS + OVERHEAD_BUDGET_MS <= EMPLOYERS_HANDOFF_TIMEOUT_MS` (`9000 + 5000 = 14000 <= 20000`) holds with 6000ms of genuine real-world slack — not a 1000ms token margin that a cold Fly machine or a large attachment could blow through. On Cloudflare Workers, wall-clock time spent awaiting `fetch` is NOT CPU-billed, so a larger outer ceiling costs nothing while meaningfully protecting the fail-safe guarantee. **Do NOT shrink Plan 33-01's inner timeouts further to compensate** — 4s/5s upstream is already tight against a cold Fly machine; this Worker's outer ceiling is the number that has room to grow, and it has grown. **This invariant is enforced mechanically, not by comment discipline or by either package's own self-referential test:** Plan 33-04 builds `scripts/check-email-timeout-invariant.mjs`, a root-level CI check that reads the real constants out of BOTH this file and `apps/startup/workers/routes/email.ts` and fails loudly (printing both sides' actual numbers) if the inequality is violated. This plan's own unit test (Task 2) only sanity-checks THIS package's numbers in isolation — it is explicitly NOT the cross-package guard, and must not be described as one.

Purpose: this is the other half of the inbound-email gap closure — without it, mail to `<slug>@employers.internjobs.ai` currently lands here (via the catch-all) and is silently redirected to the operator's personal Gmail with no path to the startup pipeline.
Output: `apps/email-worker/src/index.js` gains an `employers.internjobs.ai` dispatch branch; first-ever test file for this Worker; CI job so it's no longer untested in the pipeline; `wrangler.toml`'s routing-topology documentation corrected to match the live, phase-33-verified reality.

```js
// Phase 33 latency budget (checker blocker fix, iteration 2): this outer
// timeout wraps a handoff whose receiving end (apps/startup's
// processInboundEmail) makes two SEQUENTIAL upstream fetches timed at
// RESOLVE_TIMEOUT_MS (4000ms) + INSERT_TIMEOUT_MS (5000ms) = 9000ms max.
// That 9000ms is NOT the whole story: the outer POST this timeout wraps also
// pays for TLS/connection setup + transmission of the raw MIME body, and
// postal-mime parsing CPU that runs BETWEEN the two inner fetches on the
// receiving end (budgeted in neither inner timeout). OVERHEAD_BUDGET_MS below
// covers that non-fetch time. The full invariant this pair must satisfy is:
//   RESOLVE_TIMEOUT_MS + INSERT_TIMEOUT_MS + OVERHEAD_BUDGET_MS <= EMPLOYERS_HANDOFF_TIMEOUT_MS
// i.e. 4000 + 5000 + 5000 = 14000 <= 20000 (6000ms real slack). This is
// enforced in CI by scripts/check-email-timeout-invariant.mjs (Plan 33-04),
// which reads the real constants from both this file and apps/startup's
// email.ts — NOT by this comment, and NOT by either package's own
// self-referential unit test. If you change any of these three numbers,
// the CI script (not a human re-reading this comment) is what will catch a
// resulting violation. Wall-clock time spent awaiting fetch() is not
// CPU-billed on Workers, so keeping this ceiling generous costs nothing.
const OVERHEAD_BUDGET_MS = 5000;
const EMPLOYERS_HANDOFF_TIMEOUT_MS = 20000;

export async function dispatchToEmployersHandoff(message, toAddress, fromAddress, env) {
  if (!env.STARTUP_EMAIL_HANDOFF_URL || !env.EMAIL_HANDOFF_SECRET) {
    console.log(JSON.stringify({
      level: "warn",
      message: "employers_handoff_unconfigured",
      to: toAddress,
    }));
    return false;
  }
  let rawBuf;
  try {
    rawBuf = await new Response(message.raw).arrayBuffer();
  } catch (err) {
    console.log(JSON.stringify({
      level: "error",
      message: "employers_handoff_raw_read_failed",
      error: String(err?.message ?? err),
      to: toAddress,
    }));
    return false;
  }
  try {
    const res = await fetch(env.STARTUP_EMAIL_HANDOFF_URL, {
      method: "POST",
      headers: {
        "content-type": "message/rfc822",
        "authorization": `Bearer ${env.EMAIL_HANDOFF_SECRET}`,
        "x-startup-to": toAddress,
        "x-startup-from": fromAddress ?? "",
      },
      body: rawBuf,
      signal: AbortSignal.timeout(EMPLOYERS_HANDOFF_TIMEOUT_MS),
    });
    if (!res.ok) {
      console.log(JSON.stringify({
        level: "warn",
        message: "employers_handoff_non_2xx",
        status: res.status,
        to: toAddress,
      }));
      return false;
    }
    return true;
  } catch (err) {
    console.log(JSON.stringify({
      level: "warn",
      message: "employers_handoff_fetch_failed",
      error: String(err?.message ?? err),
      to: toAddress,
    }));
    return false;
  }
}
```
