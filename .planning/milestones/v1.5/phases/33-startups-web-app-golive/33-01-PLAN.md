<objective>
Give the startup Worker (`internjobs-startup-mcp`, deployed at `mcp.internjobs.ai`) an HTTP entry point that a second Worker can hand inbound employers-domain mail off to, and refactor the existing CF-native `email()` handler to share the same resolve/parse/insert core so there is exactly one implementation of "route an employers.internjobs.ai email to the right startup."

**Why an HTTP handoff and not a second CF Email Routing rule:** live investigation during this phase (see phase context / `.planning/workstreams/team-workspace/PHASES-33-36-HANDOFF.md` predecessor docs) confirmed via the CF API that Cloudflare Email Routing has exactly **one zone-wide catch-all** for `internjobs.ai` (`matchers:[{type:"all"}]`), already bound to Worker `internjobs-email-ingest` (`apps/email-worker`). The dashboard's per-subdomain dropdown is only a filtered *view* of that one rule — there is no way to add a second, independent catch-all scoped to `employers.internjobs.ai` without repointing (and breaking) the existing `agent.internjobs.ai` conversation-alias ingestion. So `apps/startup/workers/app.ts`'s `email()` export (wired in Phase 28.5) is currently **orphaned** — CF never invokes it. The chosen fix (this plan + Plan 33-02): `apps/email-worker` becomes the single mail dispatcher and, for `@employers.internjobs.ai` recipients, hands the raw MIME off over HTTPS to a new endpoint on THIS Worker, reusing all of `handleInboundEmail`'s existing slug-resolution + MIME-parse + insert logic instead of duplicating it in the (plain-JS, schema-agnostic) email-worker.

**Contract with Plan 33-02 (apps/email-worker) — both plans must match this exactly, they run in parallel and do not read each other's code:**
- URL: `https://mcp.internjobs.ai/internal/email/inbound` (routed via the Worker's existing `mcp.internjobs.ai` custom domain — no new DNS/CF config needed)
- Method: `POST`
- Headers: `Authorization: Bearer <EMAIL_HANDOFF_SECRET>` (new shared secret, provisioned in Plan 33-04), `Content-Type: message/rfc822`, `X-Startup-To: <recipient address, e.g. acme@employers.internjobs.ai>`, `X-Startup-From: <CF's message.from header value>`
- Body: the exact raw MIME bytes CF handed the email-worker (an `ArrayBuffer`/octet body, NOT JSON-wrapped)
- Response: `200 {ok:true, duplicate?:boolean, id?:string}` on success. Non-2xx on any failure — the caller (email-worker) treats ANY non-2xx, timeout, or thrown error as "fail safe": forward the original mail to its existing operator fallback inbox. Specifically: `400` invalid recipient, `401` bad/missing auth, `404` unknown slug (channel link not found), `422` MIME parse failure, `502` resolve/insert infra failure.
- **End-to-end latency budget (fixes a checker-flagged blocker — read carefully, this is a cross-plan contract, not just an internal implementation detail):** this Worker's `processInboundEmail()` makes TWO SEQUENTIAL upstream fetches (`/v1/channels/resolve` then `/v1/messages/inbound`). Their timeouts are reduced by this plan to **4000ms + 5000ms = 9000ms max inner latency** (down from the pre-existing 8000ms/10000ms this code inherited from the original `handleInboundEmail`, which summed to 18s — a mismatch against Plan 33-02's 10s outer ceiling that would cause spurious operator-forward duplicates on merely-slow-but-successful requests). **This plan (33-01) owns the inner-sum number.** Plan 33-02 owns the outer handoff timeout and keeps it at `10000ms`, i.e. ≥ inner-sum + 1000ms margin. If you change either inner timeout here, you MUST also re-check Plan 33-02's outer timeout stays ≥ the new inner sum — a silent mismatch here is exactly the defect this note exists to prevent.

Purpose: closes the inbound-email gap for the startup pilot — without this, mail to a founder's agent email currently silently forwards to the operator's personal inbox instead of reaching `inbound_messages`.
Output: `apps/startup/workers/routes/email.ts` refactored with a shared core + new route; `apps/startup/workers/app.ts` mounts the route; `apps/startup/workers/types.ts` gains the new secret; test coverage for both entry points.

```ts
import { Hono } from "hono";
export const emailInternalRouter = new Hono<{ Bindings: Env }>();

async function verifyEmailHandoffSecret(provided: string, env: Env): Promise<boolean> {
  // constant-time compare, mirror apps/startup/workers/routes/admin.ts::verifyAdminSecret
  // against env.EMAIL_HANDOFF_SECRET
}

emailInternalRouter.post("/email/inbound", async (c) => {
  const provided = c.req.header("Authorization")?.replace(/^Bearer\s+/i, "") ?? "";
  if (!(await verifyEmailHandoffSecret(provided, c.env))) {
    return c.json({ error: "unauthorized" }, 401);
  }
  const toAddress = (c.req.header("X-Startup-To") ?? "").toLowerCase().trim();
  if (!toAddress || !toAddress.endsWith("@employers.internjobs.ai")) {
    return c.json({ error: "invalid_recipient" }, 400);
  }
  const fromAddressHeader = c.req.header("X-Startup-From") ?? null;
  const rawBytes = await c.req.arrayBuffer();
  const result = await processInboundEmail({ toAddress, fromAddressHeader, rawBytes, env: c.env });
  if (result.ok) {
    return c.json({ ok: true, duplicate: result.duplicate, id: result.id }, 200);
  }
  const statusByReason = { unknown_slug: 404, resolve_failed: 502, parse_failed: 422, insert_failed: 502 } as const;
  return c.json({ ok: false, reason: result.reason }, statusByReason[result.reason]);
});
```
